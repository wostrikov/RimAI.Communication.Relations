## Уніфікація текстів вимкнення та затримки відновлення для запиту завдання на нагородження (v0.9.1024)

- У цій версії немає нових параметрів, доступних для налаштування користувачем.
- Зміни фіксованої поведінки:
  - Із доступного набору завдань `create_quest` вилучено `BestowingCeremony`; меню запиту завдання більше не показує церемонію нагородження.
  - Коли зовнішній/старий промпт примусово запитує `BestowingCeremony`, рівень виконання негайно повертає помилку `bestowing_disabled` і записує доступний для пошуку якір журналу.
  - Підказку про затримку відновлення дипломатії `[?]` уніфіковано для відображення в ігровому часі (дні/години); залишкові секунди більше не пояснюються через реальний час.
- Примітки щодо сумісності:
  - Не змінюються структура збережень, ключ зберігання затримки відновлення та зовнішнє ім’я ключа дії JSON.
  - Лише звужуються видимість шаблонів завдань і спосіб тлумачення текстів затримки відновлення, щоб уникнути забруднення подальшого процесу нагородження порожніми запитами на нагородження.

## Резервний варіант за відсутності `/models` і прямий вивід структурованого оригінального тексту (v0.9.1023)

- У цій версії немає нових параметрів, доступних для налаштування користувачем.
- Зміни фіксованої поведінки:
  - Коли діагностика доступності API повертає `/models`, використовуйте резервне chat-зондування для визначення доступності через `404/405/501`, більше не вважаючи помилку безпосередньо невдачею.
  - Локальна перевірка сумісності OpenAI за відсутності `/v1/models` більше не вважає службу негайно офлайн; натомість продовжується остаточна перевірка через chat.
  - RPG/Після вичерпання повторних спроб структурована дипломатична відповідь більше не вставляє фіксовану фразу імерсивного резервного варіанта, а безпосередньо виводить оригінальний текст.

- Примітки щодо сумісності:
  - Структуру збережень і зовнішні ключі дій JSON не змінено.
  - Змінено лише критерії діагностики та стратегію резервного варіанта для структурованих помилок, щоб уникнути ситуацій «інтерфейс доступний, але перевірка не пройдена» і «фіксований текст поглинає відповідь».

## Виправлення основи завантаження та перевірки конфігурації моделі Google API (v0.9.79)

- У цій версії немає нових налаштувань, доступних для зміни користувачем.
- Незмінна зміна поведінки:
  - Коли provider вибрано як `Google`, а `Base URL` залишено порожнім, завантаження списку моделей і швидка перевірка з’єднання й надалі використовують вбудовану стандартну кінцеву точку Google, тож помилка «URL не може бути порожнім» більше не з’являється помилково.
  - `测试连通性` тепер перевіряє лише «чи існує ввімкнена хмарна конфігурація із заповненим ключем API», і більше не повідомляє безпосередньо «немає дійсної конфігурації», якщо модель ще не вибрано.
  - `测试可用性` і надалі вимагає вибрати модель, але якщо модель не вибрано, безпосередньо показує точне повідомлення «Модель не може бути порожньою, спочатку завантажте й виберіть модель».
  - До розбору списку моделей Google додано резервне вилучення поля `name`, щоб зменшити ймовірність появи порожнього меню моделей через зміни порядку полів або зайві поля у відповіді сервера.
- Примітки щодо сумісності:
  - Структуру збережень не змінено.
  - Основний ланцюжок запитів чатів під час роботи не змінено.
  - Зміни стосуються лише поведінки завантаження моделей, швидкої перевірки з’єднання та попередньої перевірки доступності на сторінці налаштувань API.

## Основний протокол структурування діалогів і вихід основного ланцюжка міркувань (v0.9.71)

- У цій версії немає нових перемикачів функцій, доступних для зміни користувачем.
- Незмінна зміна поведінки:
  - Відповіді моделі для RPG / дипломатії / активних push-сповіщень за замовчуванням мають повертати один структурований об’єкт JSON, основним полем якого є `visible_dialogue`, а `actions` з’являється лише за наявності фактичного ефекту gameplay.
  - Старий формат «діалог + кінцевий список actions JSON» зберігається лише для мінімальної сумісності введення й більше не є основним протоколом.
  - Для вихідних даних додано протокол fail-fast; якщо структура некоректна, спочатку виконується повторна спроба, а потім використовується локальна безпечна відповідь, замість того щоб і далі напряму передавати некоректний оригінальний текст у UI.
  - thought-chain за замовчуванням вимкнено для всіх каналів; навіть якщо старе поле конфігурації збережено, воно більше не є межею безпеки під час виконання.
- Примітки щодо сумісності:
  - Нові поля збережень не додаються, читання старих збережень не порушується.
  - У робочій області промптів усе ще можна бачити вузли й конфігурацію thought-chain, але за замовчуванням вони не входять до основного ланцюжка виконання.

  - Фіксована помірно м’яка масова система штрафів: час на звільнення +50%, коефіцієнт штрафу за звичайне прострочення/зниження ціни 0.7, поріг зниження ціни підвищено.
  - Нове покарання за відсутність органів у пакетному режимі зберігає інтенсивність для одного персонажа, без послаблень.

## Протокол імпорту Prompt Bundle до робочого середовища (Fail Fast)

- Імпорт до робочого середовища приймає лише `RimChat_PromptBundle.json` (протокол Prompt Bundle).
- Точка входу імпорту спочатку виконує жорстку структурну перевірку; мають одночасно виконуватися такі умови:
  - Містить `BundleVersion`
  - Містить `IncludedModules`
  - Містить щонайменше одне поле Bundle payload (наприклад, `SystemPrompt` / `DiplomacyDialoguePrompt` / `PawnDialoguePrompt` / `SocialCirclePrompt` / `FactionPromptsJson`)
- Якщо виявлено `Presets` / `ChannelPayloads` / `UnifiedPromptCatalog`, файл буде визначено як файл `PromptPresets` і імпорт негайно відхилено.
- Не-Bundle JSON (або недійсний JSON / порожній файл) негайно завершується помилкою з чітким поясненням причини; повернення до «безпосереднього імпорту об’єкта за замовчуванням» не виконується.
- Протокол експорту не змінюється; за замовчуванням виводиться `RimChat_PromptBundle.json`.

## Семантика конфігурації єдиного джерела робочого простору промптів（v0.7.55）

- Єдине джерело:
  - Офіційне редагування в робочому просторі записує лише `PromptUnifiedCatalog`（sections + nodes + node layout + template aliases）。
  - `PromptSectionCatalog` більше не є офіційним джерелом для запису, а використовується лише для legacy-імпорту/експорту.
- Момент збереження в робочому просторі:
  - На етапі редагування section/node/node-layout оновлюється лише unified у пам’яті.
  - Лише явне натискання `Save` у робочому просторі записує `PromptUnifiedCatalog_Custom.json` і поточний preset для постійного збереження.
  - Перемикання section/node/channel/preset не запускає автоматичний запис на диск.
- пресет payload:
  - З офіційних полів вилучено `PromptSectionCatalog`, залишається лише `UnifiedPromptCatalog`.
  - Якщо старий файл preset містить поле section, під час імпорту воно односторонньо переноситься до unified, після чого старе поле більше не записується назад.
- власне сховище RPG:
  - `Prompt/Custom/PawnDialoguePrompt_Custom.json` більше не зберігає `PromptSectionCatalog` постійно.
  - Старе поле діє лише на етапі читання під час міграції, після читання воно об’єднується з unified.
- Керування побічними ефектами читання:
  - Попередній перегляд/UI проходить через `LoadConfigReadOnly()`, заборонено «запускати виправлення із записом на диск лише під час попереднього перегляду».
  - Якщо потрібно виконати виправлення із записом назад, використовуйте явний виклик `RepairAndRewritePromptDomains()`.

## Пресети та взаємодія з редактором робочого столу промптів (v0.7.54)

- Пресети за замовчуванням доступні лише для читання (без нових зовнішніх параметрів конфігурації):
  - Пресет за замовчуванням має стабільний ідентифікатор `DefaultPresetId`, визначений шаром сховища.
  - Під час першого наміру редагувати пресет за замовчуванням (зміна тексту, перейменування в рядку, зміна структури вузлів, запис швидкої дії, запис Reset) автоматично створюється відгалуження до нового пресету, який стає об’єктом редагування.
  - Формат назви автоматично створеного відгалуження: `Custom yyyyMMdd-HHmmss`.
- Взаємодія зі списком пресетів:
  - Зберігається верхній елемент `新建/复制`.
  - До рядків списку додано швидкі дії: копіювати, видалити.
  - Подвійне клацання назви пресету дає змогу перейменувати її в рядку (Enter або втрата фокуса — зберегти, Esc — скасувати).
  - Точка входу для видалення пресету за замовчуванням вимкнена; подвійне клацання його назви спочатку автоматично створює відгалуження, а потім переходить до перейменування.
- Панель дій головного редактора:
  - Панель інструментів фіксовано містить `Undo / Redo / Save / Reset`.
  - Історія Undo/Redo ізольована за принципом «пресет+канал+сегмент/вузол»; історія не змішується між об’єктами.
  - Save забезпечує негайне збереження, а Reset скидає лише поточний сегмент/поточний вузол і не впливає на інші об’єкти.
  - Обмеження перемикання fail-fast: перед перемиканням сегмента/каналу/вузла/пресета необхідно спочатку виконати примусове збереження; якщо ланцюжок збереження повертає помилку, поточне перемикання блокується, щоб уникнути відкату до старого тексту.
  - У разі помилки синхронізації пресета стан редагування залишається pending; подальше перемикання заборонене, доки ланцюжок збереження не відновить успішну роботу.
- Сумісність:
  - Якщо в старому preset store відсутній `DefaultPresetId`, його буде автоматично нормалізовано та перенесено.
  - Не додавати нових полів бізнес-промптів і не змінювати основну структуру старих збережень.

  - Нові перемикачі для користувача не додаються; це виправлення коригує типові значення єдиного каталогу.

## Узгодженість життєвого циклу Prompt Unified Catalog（v0.7.25）

- Область дії:
  - Шляхи читання й запису вузлів `PromptUnifiedCatalog` і читання й запису компонування вузлів.
  - `RimChatSettings_RimTalkCompat.EnsureUnifiedCatalogReady()` запускає процес нормалізації.
- Правила поведінки:
  - Ланцюжок вузлів переходить на сувору перевірку каналів; невідомий або порожній `promptChannel` більше не виконує мовчазний відкат до `any`.
  - У разі некоректного `nodeId` або коли «вузол не належить до allowlist поточного каналу», `ResolveNode/ResolveNodeLayout/SetNode/SetNodeLayout` негайно викидає виняток (fail-fast).
  - Нормалізацію під час запуску переведено в режим звітування: результати очищення зводяться через `PromptUnifiedCatalogNormalizeReport`, щоб уникнути шуму від окремих записів про помилки.
- Стратегія збереження:
  - Умову збереження під час запуску змінено на: `legacy迁移变化 || migration版本变化 || normalizeReport.HasStructuralChange`.
  - Під час першого завантаження старої конфігурації її буде автоматично очищено й збережено один раз; надалі для тієї самої конфігурації очищення та запис на диск не повторюються.
- Рівні журналювання:
  - `Error`: порушення інваріанта, що блокує виконання (до викидання винятку).
  - `Warning`: зведення автоматичного очищення (невідомі канали, видалені некоректні вузли/компонування).
  - `Info`: кількість доповнених елементів компонування за замовчуванням, повідомлення про завершення міграції.
- Сумісність:
  - Не додавати нові користувацькі параметри, не змінювати файли самої гри.
  - Сумісність зі старими збереженнями забезпечується через «одноразове очищення + одноразове збереження», без мовчазного толерантного читання.

## Мінімальний user-контракт для повідомлень запиту（v0.7.24）

- Область дії:
  - Усі точки входу запитів AI під час виконання（асинхронний `AIChatServiceAsync` + синхронний `AIChatService`）。
- Правила поведінки:
  - Якщо список повідомлень запиту непорожній, але не містить дійсного повідомлення `user`, перед надсиланням автоматично додається одна мінімальна інструкція `user`.
  - Недійсний `role` перед надсиланням нормалізується до `user`, щоб уникнути відхилення через перевірку параметрів provider.
- Вплив на конфігурацію:

- Відображення каналів робочого столу:
  - Набір доступних каналів і канал, що використовується під час виконання, спільно визначаються через `PromptSectionSchemaCatalog`; у UI і під час виконання більше немає окремих жорстко заданих списків.

## Уніфіковане розташування вузлів（v0.7.19）

- Розташування конфігурації:
  - `Prompt/Custom/PromptUnifiedCatalog_Custom.json` -> `channels[].nodeLayout[]`
- Поля `nodeLayout`:
  - `nodeId`: вузол ID (наприклад, `fact_grounding`)
  - `slot`: слот вузла (5 фіксованих значень)

    - `main_chain_after`
    - `dynamic_data_after`

  - Якщо в старій конфігурації немає `nodeLayout`, під час запуску його буде автоматично доповнено в історичному порядку та збережено;

- Поведінка робочого столу:
  - У режимі вузлів можна перетягуванням змінювати порядок, переміщувати вгору або вниз, перемикати слоти, вмикати чи вимикати вузли;
  - Попередній перегляд праворуч показує порядок розміщення вузлів і повний попередній перегляд складання.

## Єдиний набір правил користувацьких змінних + безпечний експорт особистості (v0.7.16)

- Доступним для запису користувацьким простором імен і надалі є лише:
  - `system.custom.{key}`
  - під час збереження `key` нормалізується до нижнього регістру slug, дозволено лише `a-z0-9_`.
- Поля збереження оновлено до трирівневої структури:
  - `UserDefinedPromptVariables`
    - поля кожного елемента: `Id`, `Key`, `DisplayName`, `Description`, `DefaultTemplateText`, `Enabled`
  - `UserDefinedPromptVariableFactionRules`
    - поля кожного елемента: `Id`, `VariableKey`, `FactionDefName`, `Priority`, `TemplateText`, `Enabled`, `Order`
  - `UserDefinedPromptVariablePawnRules`
    - поля кожного елемента: `Id`, `VariableKey`, `NameExact`, `FactionDefName`, `RaceDefName`, `Gender`, `AgeStage`, `TraitsAny`, `TraitsAll`, `XenotypeDefName`, `PlayerControlled`, `Priority`, `TemplateText`, `Enabled`, `Order`
- Сумісність зі старою конфігурацією:
  - Старий `FactionScopedPromptVariableOverrides` досі можна прочитати;
  - Після читання його буде автоматично перенесено до нової faction rule;
  - Подальше збереження записуватиме лише нову модель правил і більше не записуватиме старі поля.
- Розбір під час виконання:
  - У каталозі змінних і надалі відображатиметься лише один шлях `system.custom.xxx`;
  - Порядок збігів фіксований:
    - `pawn exact`
    - `pawn conditional`
    - `faction`
    - `default template`
    - Порожній рядок
  - Порядок сортування в одному рівні фіксований:
    - `Priority` від більшого до меншого
    - `Specificity` від більшого до меншого
    - `Order` від меншого до більшого
- Область відповідності правил для персонажа:
  - RPG Сценарій має пріоритет під час відповідності `Target`;
  - Якщо `Target` порожній, використовується запасний варіант `Initiator`;
  - Якщо в дипломатичному сценарії немає доступного персонажа, правила для персонажа пропускаються.
- `pawn.personality` безпечне відкриття:
  - Початкова особистість, як і раніше, надходить із наявних даних середовища виконання;
  - `system.custom.pawn_personality_override` може безпечно перевизначати експортовані значення промпту;
  - `system.custom.pawn_personality_append` додаватиме текст після дійсної особистості;
  - Базові дані гри не змінюються — змінюються лише експортовані значення промпту під час рендерингу.
- Редагування та перевірка:
  - Змінні користувача, правила фракції та правила персонажа підтримують змінні простору імен strict Scriban;
  - Під час збереження блокуються:
    - Дубльовані key
    - Конфлікти шляхів
    - Недійсний `FactionDefName / RaceDefName / XenotypeDefName / TraitDefName / AgeStage / Gender / PlayerControlled`
    - Помилка компіляції Scriban
    - Посилання на невідому змінну
    - Циклічна залежність користувацьких змінних
- Правила видалення:
  - Перед видаленням змінної виконується пошук у `PromptSectionCatalog`, RimTalk compat, persona copy, інших шаблонах за замовчуванням користувацьких змінних, Faction Rule і Pawn Rule;
  - Якщо виявлено посилання, видалення блокується, а джерело показується;
  - Видалення глобальної змінної також видаляє всі її faction/pawn правила.
- UI：
  - Браузер спільних змінних підтримує точки входу для створення «порожньої змінної + офіційної прикладної змінної»;
  - Редактор розділено на «Основна інформація / Шаблон за замовчуванням / Список правил»;
  - Список правил розділено на дві вкладки: `Faction Rules` і `Pawn Rules`;
  - `system.custom.*` і надалі підтримує редагування/видалення;
  - Вбудовані змінні та змінні-мости й надалі доступні лише для читання.

## Уніфікація роботи дипломатичного промпту + XML-подібна оболонка секції (v0.7.14)

- Офіційне джерело промпту під час роботи дипломатії:
  - Звичайна дипломатія: використовує лише `BuildFullSystemPrompt(...)`, надсилається лише 1 system prompt.
  - Стратегічна рекомендація: використовувати лише `BuildDiplomacyStrategySystemPrompt(...)` і надсилати лише 1 окремий system prompt.
  - Мережевий рівень більше не додає `Think step by step.` / `Review your rules.`.
- Основне джерело офіційного тексту правил:
  - `Prompt/Default/PromptSectionCatalog_Default.json`
  - Розгорнуті природномовні правила для дипломатії та `diplomacy_strategy` тепер уніфіковано підтримуються в каталозі секцій.
- Поля дзеркала сумісності:
  - `GlobalSystemPrompt`
  - `GlobalDialoguePrompt`
  - `UseHierarchicalPromptFormat`
  - Наведені вище поля знижено до ролі compatibility mirror; вони більше не визначають структуру промпту під час виконання.
- Стандартний `SystemPrompt_Default.json`:
  - `GlobalSystemPrompt` зберігає лише текст підказки compatibility mirror; під час офіційного виконання великі пакети правил у ньому більше не зчитуються.
- Остаточний формат продукту:
  - Фіксований envelope-подібний формат XML.
  - `main_prompt_sections` більше не виводить текст `[SECTION: ...]`, а виводить стабільні дочірні вузли секцій `<system_rules>`, `<character_persona>`, `<action_rules>` тощо.
  - Готовий промпт під час виконання більше не містить забруднення вихідними мітками `[FILE]` / `[CODE]`.

## Джерело вмісту записів за замовчуванням для всіх каналів (v0.6.23)

  - `Prompt/Default/RimTalkPromptEntries_Default.json`
- Структура даних：

    - `Sections[]`
      - `SectionId`: фіксовані 8 сегментів ID（`system_rules`、`character_persona`、`memory_system`、`environment_perception`、`context`、`action_rules`、`repetition_reinforcement`、`output_specification`）

  - Під час виконання спочатку читається цей JSON;
  - У разі помилки читання використовується вбудований fallback;

## Руйнівне перемикання головного рушія Scriban (v0.6.16)

- Головна точка входу рендерингу:
  - Уніфіковано до `IScribanPromptEngine.RenderOrThrow(...)`.
- Правила змінних:
  - Дозволені лише змінні простору імен: `ctx.* / pawn.* / world.* / dialogue.* / system.*`.
  - Заборонено використовувати непов’язані змінні (наприклад, `{{scene_tags}}`).
- Стратегія обробки помилок:
  - Parse/Render/невідомі змінні/доступ до порожнього об’єкта — усі спричиняють `PromptRenderException`.
  - У разі помилки рендерингу заборонено повертатися до оригінального тексту або мовчки продовжувати виконання.
- Стратегія міграції:
  - Старі шаблони переносяться до змінних простору імен за допомогою автоматичного переписувача відповідно до таблиці відповідностей.
  - Після переписування негайно виконується перевірка Scriban; шаблони з помилками позначаються як `Blocked` і блокують виклик.
- Ланцюжок виконання:
  - Основний ланцюжок більше не залежить від методу рендерингу під час виконання `RimTalkCompatBridge`.
  - Браузер змінних замінено на локальний знімок `PromptVariableCatalog`.
- Моніторинг продуктивності:
  - Кеш компіляції Scriban має фіксований обсяг LRU.
  - Вікно налагодження API відображає коефіцієнт влучань у кеш, кількість влучань/промахів/витіснень, середній час компіляції та середній час рендерингу.

> Примітка: якщо в описі старої версії нижче трапляється згадка «fallback/відкат суміснісного мосту», це історичний запис; під час виконання v0.6.15+ слід керуватися правилами strict із цього розділу.

## Редагування записів змінних каналу RimTalk (v0.6.3)

- `PromptEntries`
  - Тип: `List<RimTalkPromptEntryConfig>`
  - Призначення: зберігає вміст редагування записових промптів дочірнього каналу RimTalk (може використовуватися для формування на основі змінних)
- `RimTalkPromptEntryConfig`
  - `Id`: унікальний ідентифікатор запису
  - `Name`: назва запису, що відображається
  - `Role`: роль запису (`System/User/Assistant`)

  - `Content`: основний текст шаблону запису (підтримує змінні token)
- Примітки щодо сумісності:
  - якщо стара конфігурація містить лише `CompatTemplate`, її буде автоматично перенесено до запису за замовчуванням;
  - результат редагування запису автоматично об’єднується назад у `CompatTemplate`, щоб забезпечити сумісність зі зчитуванням старими версіями.

## Безпечне зіставлення Custom URL і перемикач режиму (v0.4.9)

- На сторінці налаштувань API (Custom provider) додано режим URL:
  - `Base URL`: режим базової адреси, автоматично доповнює кінцеву точку чату за консервативними правилами.
  - `Full Endpoint`: режим повної кінцевої точки, надсилає запит точно за введеним URL.
- Стратегія сумісності зі старою конфігурацією:
  - Якщо URL містить `/chat/completions`, його автоматично визначено як `Full Endpoint`.
  - В інших випадках його автоматично визначено як `Base URL`.
- SiliconFlow Правила сумісності (лише Custom provider):
  - Лише хост `cloud.siliconflow.*` під час виконання зіставлятиметься з `api.siliconflow.cn`.
  - Це не вплине на інші домени `*.siliconflow.*`.
- Межі автоматичного доповнення Base URL:
  - Лише порожній шлях, `/` і `/v1` автоматично доповнюються до `/v1/chat/completions`.
  - Нестандартний кінцевий шлях зберігається без змін, а в стані перевірки з’єднання відображається підказка.
- Покращення перевірки з’єднання:
  - У режимі `Full Endpoint` спочатку перевіряється список моделей, а потім виконується резервна перевірка chat endpoint, щоб зменшити кількість помилкових висновків «можна вести діалог, але перевірка не пройдена».

  - Час до завершення терміну дії повідомлення в черзі (години).
  - Повідомлення, термін дії яких минув, автоматично відкидаються під час обробки черги.
- `EnableBusyByDrafted`
  - Критерій зайнятості: будь-який колоніст перебуває у стані призову.
- `EnableBusyByHostiles`
  - Критерій зайнятості: на карті домашньої території гравця є згенеровані ворожі юніти.
- `EnableBusyByClickRate`
  - Критерій зайнятості: кількість натискань лівою кнопкою миші за 6-секундне вікно досягає порогового значення (типово `>=12`).
- `PawnRpgProtagonistCap`（v0.5.6）
  - Максимальна кількість персонажів у PawnRPG активному «списку персонажів для ручного керування» (типово `20`, допустимий діапазон `1~100`).
  - Впливає лише на PawnRPG активний канал (зокрема примусові тригери налагодження), але не впливає на точку входу для початку розмови з RPG через ручне клацання правою кнопкою миші.
- `PawnRPG 主角名单`（v0.5.6）
  - Вхід для налаштування розташовано в тому самому розділі; підтримується додавання, видалення та очищення головних персонажів.
  - Зберігається окремо для кожного збереження (не є глобально спільним).
  - Діапазон кандидатів: усі персонажі фракції гравця; під час виконання все одно виконується фільтрація за доступністю.
- `RimChat_NpcPush_DebugForceTrigger`（кнопка налагодження UI）
  - Негайно примусово запускає один випадковий вихідний діалог (для спільного налагодження; як і раніше, залежить від доступності налаштувань AI).

### PawnRPG Фіксована стратегія роботи (не параметр конфігурації)

- Окреме обмеження NPC на 6 днів: після успішної доставки кожного NPC протягом `150000` тіків повторна оцінка/ініціювання не виконується.
- Глобальне обмеження на 3 дні: після успішної доставки повідомлення не попереджувального типу протягом `75000` тіків більше не доставляються успішно активні повідомлення PawnRPG.
- Виняток для попереджень: обходить лише глобальне обмеження на 3 дні, але не обходить окреме обмеження NPC на 6 днів.
- Налаштування порогів: для не близьких стосунків потрібно `Opinion >= 35`; поріг низького настрою для умовного спрацювання — `Mood <= 0.30`.
- Потрійна перевірка зайнятості залишається чинною: `Drafted` / ворожі одиниці / часті натискання.
- Коли NPC і персонаж гравця сплять/непритомні або працюють, спрацьовування додається до черги затримки.
- Стратегія черги без змін: стандартний ліміт для кожної фракції — `3` повідомлень, стандартний термін дії — `12` годин.
- Стратегія невдалих спроб LLM без змін: кожне повідомлення повторюється `1` разів, після послідовних невдач відкидається.
- Правило затримки відновлення: лічильники окремої NPC та глобальної затримки відновлення оновлюються лише після «успішної доставки».
- Якщо відкрити діалог з активного листа PawnRPG, це активне повідомлення одразу використовується як перша репліка сеансу; повторний запит до LLM для повторної генерації вступу не виконується.

### Стратегія роботи (не параметр конфігурації)

- У цьому розділі описано фіксовану стратегію старого активного каналу фракцій (правила каналу PawnRPG наведено в попередньому розділі).

- Інтервал оцінювання звичайного спрацьовування: `6000` тіків.
- Інтервал обробки черги: `600` тіків.
- Відновлення активних повідомлень у межах однієї фракції: після успіху випадково `1~3` днів.
- Перевірка статусу онлайн: лише `Online` можна надсилати безпосередньо, для офлайн/«не турбувати» повідомлення стають у чергу.
- Перевірка затримки відновлення сеансу: якщо діалог завершено через NPC і все ще триває затримка відновлення повторного підключення, активний запуск відкладається до завершення затримки (але все ще залежить від завершення терміну дії черги).
- Стратегія невдачі LLM: для кожного спрацьовування повторити не більше `1` разів; після невдачі відхилити й записати до журналу.

## Кнопки стратегії зниження прихильності (вікно дипломатії)

### Опис поведінки (у поточній версії налаштовувані перемикачі відсутні)

- Діє лише тоді, коли **відповідь AI у цьому раунді спричинила чисте зниження прихильності**.

## Система статусу онлайн

### Базова конфігурація (налаштування моду -> налаштування MOD -> налаштування UI -> налаштування мережевого статусу)

- `EnableFactionPresenceStatus`
  - Чи ввімкнути систему статусу онлайн фракцій.
  - Висоту відображення значків статусу онлайн у заголовку дипломатичного вікна та списку фракцій збільшено; китайські позначки статусу більше не обрізатимуться.
- `PresenceCacheHours`
  - Тривалість (у годинах) кешування статусу онлайн фракції після закриття вікна дипломатичного діалогу.
  - За замовчуванням: `2`.
  - Для позначок статусу/підказок шрифту Tiny тепер уніфіковано додано відступи; китайський текст статусу в головному інтерфейсі та дипломатичному вікні рідше обрізатиметься.
- `PresenceForcedOfflineHours`
  - Повзунок збережено для налаштування безперервності інтерфейсу; він більше не впливає на виконання примусової тривалості `go_offline/set_dnd`.
  - Поточну примусову тривалість зафіксовано: `go_offline=2小时`, `set_dnd=4小时`.
  - За замовчуванням: `24`.
- `PresenceNightBiasEnabled`
  - Чи ввімкнути правило часткового переходу офлайн уночі.
- `PresenceNightStartHour` / `PresenceNightEndHour`
  - Період визначення ночі (0–23).
  - За замовчуванням: від `22` до `6`.
- `PresenceNightOfflineBias`
  - Додатковий коефіцієнт імовірності переходу офлайн під час нічного перебування онлайн (0.0-1.0).
  - За замовчуванням: `0.65`.

### Розширені налаштування (розгорніть «Шаблон онлайн-статусу за рівнем технологій»)

- `PresenceUseAdvancedProfiles`
  - Чи ввімкнути власні шаблони онлайн-статусу за рівнем технологій.
  - За замовчуванням: `true` (за замовчуванням увімкнено вплив технологічного рівня на тривалість перебування онлайн).
- Кожен шаблон містить:
  - `PresenceOnlineStart_*`: початкова година перебування онлайн.
  - `PresenceOnlineDuration_*`: загальна тривалість перебування онлайн (години).

Шаблони, доступні для налаштування:
- `Default`
- `Neolithic`
- `Medieval`
- `Industrial`
- `Spacer`
- `Ultra`
- `Archotech`

## Семантика станів

- `Online`: можна надсилати повідомлення.
- `Offline`: вікно доступне лише для читання, надсилати повідомлення не можна.
- `DoNotDisturb`: вікно доступне лише для читання, надсилати повідомлення не можна.
  - Поточний стан триває фіксовані `3` ігрових днів, після чого повертається до стану розкладу для повторного розрахунку.

Кольори станів фіксовані:
- Онлайн: зелений
- Офлайн: сірий
- Не турбувати: червоний

## Протокол дій AI

- `exit_dialogue`: завершити поточний раунд діалогу, зберігши поточний статус «онлайн».
- `go_offline`: завершити діалог і перейти в офлайн-режим.
- `set_dnd`: увімкнути режим «Не турбувати» та припинити взаємодію.
  - В обох випадках тривалість примусово фіксована; після завершення персонаж негайно повертається онлайн, і перевірка офлайн-режиму за розкладом більше не блокує це повернення.

- Автоматичне додавання спогадів використовує лише пул позитивного розвитку; філософські/ключові спогади четвертого рівня доступні моделі лише для явного вибору в справді напружених діалогах, що знаменують переломний момент у житті.

- Якщо текст поточного повідомлення перевищує текстову область діалогового вікна RPG, після завершення введення для повідомлення вмикається розбиття на сторінки; під час перегляду історії також доступне розбиття на сторінки.
- Recruit не доповнюється автоматично; виконується лише дія Recruit з оригінального виводу моделі.
- Системну підказку вікна діалогу змінено на напівпрозору панель, що показує залишок затримки відновлення та результат перевірки пам’яті.

### Під час першого завантаження старого збереження автоматично створюється NPC профіль ( v0.3.109 )

- Умови запуску:
  - Запускається лише один раз під час «першого завантаження старого збереження, для якого ще не встановлено позначку завершення профілювання».
  - Для нового збереження за замовчуванням встановлено позначку завершення, тому цей процес не запускається.
  - Коли версія інструкцій оновлюється, стара позначка завершення автоматично втрачає чинність, і процес запускається повторно.
- Цілі охоплення:
  - Наявні на поточній мапі людські персонажі (включно з фракцією гравця).
  - Персонажі-лідери відомих видимих фракцій.
- Ланцюжок генерації:
  - За допомогою `PromptPersistenceService.BuildPawnPersonaBootstrapProfile(Pawn)` формується стислий контекст, призначений для особистості.
  - Містить лише передісторію, риси, ключові навички, роль у фракції та ідеологію.
  - Явно виключає інформацію, не пов’язану з особистістю: здоров’я, потреби, настрій, травми, спорядження, гени, тимчасові події тощо.
  - Більше не надсилає назовні запити на настанови щодо особистості LLM; копіювання/синхронізація особистості виконується лише за доступності даних RimTalk.
  - Формат шаблону фіксований:
    - `He/She is a [core temperament] person who tends to [emotional pattern], usually handles situations by [behavioral strategy], because deep down they seek [core motivation], but this also makes them [defense/weakness], often leading to [personality cost].`
  - Приклад для довідки:
    - `He is a calm and analytical person who rarely shows his emotions and tends to approach problems through careful observation and planning, because deep down he seeks control and security, but this also makes him distant and slow to trust others.`
  - Мета виводу: зберігати один рядок, орієнтацію на особистість і короткі фрази, а також узгоджено використовувати займенники, що відповідають Pawn.
- Стратегія запису:
  - Повторно використовує наявне поле збереження `SetPawnPersonaPrompt` (те саме джерело, що й для ручного редагування).
  - Записує лише в окреме поле особистості Pawn, яке «наразі порожнє», не перезаписуючи наявний власний текст.
  - Додає пріоритет автоматичного копіювання RimTalk (v0.5.10):
    - Перед генеруванням особистості AI спочатку намагається відтворити особистість за допомогою `RimTalkPersonaCopyTemplate` і записати її.
    - Діє лише для людських Pawn у колонії (`pawn.Faction == Faction.OfPlayer`).
    - Шаблон використовує строгий синтаксис Scriban; необхідно використовувати `{{ pawn.personality }}`.
    - На сторінці налаштувань RimTalk (канал RPG) додано ручну кнопку «Негайно скопіювати всі RimTalk особистості», яка одним натисканням синхронізує RimTalk особистість поточних персонажів колонії з RimChat і повертає статистику оновлених/очищених/без змін/пропущених.
    - Якщо результат порожній або сталася помилка, негайно викидається виняток і ланцюжок переривається (без fallback).
  - У разі помилки виконується повторна спроба; після невдалої повторної спроби записується шаблонний запасний текст особистості, щоб поле не залишалося порожнім.

## Система підказок середовища (v0.3.23) ​​

### Вхід до налаштувань (Налаштування моду -> Дипломатичні діалоги -> Підказки середовища)

- `Worldview.Enabled` / `Worldview.Content`
  - Глобальний шар підказок для світу. Після ввімкнення він додається на початку двох ланцюжків системних підказок: дипломатії та RPG.

  - Загальний перемикач підказок сцени.

- `SceneSystem.MaxTotalChars`
  - Загальний жорсткий ліміт кількості символів шару сцени (за замовчуванням `4000` символів).
- `SceneSystem.PresetTagsEnabled`
  - Чи ввімкнено автоматичні системні мітки (`channel:*` / `source:*` / `scene:*`, а також мітки стосунків, настрою, здоров’я тощо).
- `EventIntelPrompt.Enabled`
  - Головний перемикач ін’єкції пам’яті про події (увімкнено за замовчуванням).
- `EventIntelPrompt.ApplyToDiplomacy` / `EventIntelPrompt.ApplyToRpg`
  - Перемикач каналів застосування пам’яті про події.
- `EventIntelPrompt.IncludeMapEvents`

  - Максимальна кількість символів у блоці пам’яті подій (за замовчуванням `1200`).

- Охоплення каналів: ручна дипломатія/активна дипломатія/ручний RPG/активний RPG спільно використовують ту саму бібліотеку сцен.

- Фактичне обмеження: система додаватиме блок фактичних обмежень; AI може відповідати лише на основі відомої інформації, а щодо тверджень без підстав має чітко зазначати невизначеність і висловлювати заперечення.

## Схема домену промптів + аварійне завершення під час виконання（v0.7.24）

- `SystemPromptDomainConfig.PromptDomainSchemaVersion`
  - Версія домену однієї опорної точки (поточна реалізація: `1`).
  - Під час завантаження, якщо версія нижча за поточну, одноразово запускається міграція зі зворотним записом і реєструється журнал міграції (стара версія -> нова версія + короткий опис виправлень).

- Самовідновлення під час запуску
  - Умова спрацювання: семантика конфігурації домену промптів неповна (наприклад, у `ApiActions` бракує ключової дії, `ResponseFormat.JsonTemplate` порожнє, шаблон ключового вузла порожній).
  - Ланцюжок читання лише з default: якщо пряма десеріалізація за доменами завершується помилкою, автоматично перемикається на агрегацію лише з default JSON, виконується відновлення, а потім семантична перевірка.
  - Кроки самовідновлення (коли семантика default-only проходить):
    1. Спочатку створити резервну копію `Prompt/Custom` у `Prompt/Custom/_backup/<yyyyMMdd_HHmmss>/`.
    2. Відновити конфігурацію виконання через шлях завантаження default-only (не читати custom).
    3. Автоматично записати результат назад у custom, щоб забезпечити ідемпотентність наступних запусків.
  - Стратегія помилки семантики default-only:
    1. Якщо кешована конфігурація вже є, зберегти кеш і заблокувати запис auto-heal назад.
    2. Якщо кешованої конфігурації немає, викинути `PromptRenderException` та заблокувати виконання за принципом fail-fast.

- Негайне припинення виконання (fail-fast) під час роботи (дипломатія/стратегія/RPG основний ланцюжок)
  - Якщо ключовий вузол runtime порожній, негайно викинути `PromptRenderException` і заблокувати запит (без подальшого непомітного переходу до спрощеного режиму).
  - Якщо `ResponseFormat.JsonTemplate` порожній, негайно заблокувати.
  - Коли `send_image` вимкнено, це відображається лише дією blocked і не впливає на додавання інших дипломатичних дій.

- Зміни правил джерел дій
  - `ApiActions` береться лише з дипломатичної сфери `DiplomacyDialoguePrompt_*`.
  - `SocialCirclePrompt_*` у соціальній сфері відповідає лише за тексти соціальних шаблонів і більше не бере участі в об’єднанні таблиць дій.

## Політика цілісності тексту під час виконання（v0.7.48）

- Перевірка цілісності видимих реплік (дипломатія/RPG)
  - Область застосування: `DialogueUsageChannel.Diplomacy`, `DialogueUsageChannel.Rpg`.
  - Стратегія повторних спроб: після виявлення правил щодо спотворених символів/фрагментів автоматично повторити той самий ланцюжок запиту 1 раз.
  - Стратегія помилки: якщо під час другої спроби проблема повторюється, повернути локальний текст-запасний варіант для занурення, не показуючи початковий результат із помилкою.

- Контроль якості перед збереженням резюме
  - Уніфіковане очищення перед збереженням: видалення керувальних символів, нормалізація пробілів, обрізання довжини.
  - Визначення аномалій: символи заміни, аномальне співвідношення друкованих символів, аномальна частка фрагментів тощо.
  - Стратегія виправлення: для аномального резюме виконується лише 1 спроба запиту на виправлення; якщо виправлення не вдалося, резюме не зберігається, а записується попередження.

- Заповнювачі стилю Faction
  - Якщо в Faction Prompt виявлено `{{ ... }}`, використовується суворий рендеринг Scriban.
  - Змінна settlement впроваджується під час виконання:
    - `world.faction_settlement_summary`
    - `world.faction_settlement.settlement_count`
    - `world.faction_settlement.nearest_to_player_home`
    - `world.faction_settlement.all_settlements`
  - У шаблоні Faction можна записувати сумісні заповнювачі: `{{ SettlementCount }}` / `{{ NearestToPlayerHome }}` / `{{ AllSettlements }}` (перед рендерингом вони зіставляються з нормативними змінними).
